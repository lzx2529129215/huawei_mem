## 1. 整体架构

### 1.1 两层预测模型

```

│                        USER SPACE                                   │
│  ┌───────────────────────────────────────────────────────────────┐  │

│  │  输入: 最近 N 个前台应用的历史序列                               │  │
│  │  输出: 预测下一个将被使用的应用 (如 QQ)                          │  │
│  │  动作: 调高预测应用的 demote_wmark，调低无人使用的应用的 demote  │  │

│                              │                                       │

│                        KERNEL SPACE                                  │
│                              ▼                                       │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  mm/tier2_watermark.c  ─── headroom < demote_wmark 触发 ──────│  │
│  │                              │                                  │  │
│  │  ┌───────────────────────────▼─────────────────────────────┐  │  │
│  │  │  tier2_predict_adjust_pages()                            │  │  │
│  │  │                                                          │  │  │
│  │  │  1. 读取 history_map[app_id] → 最近 4 个操作              │  │  │

│  │  │  4. 调整 MGLRU generation: 预测页面 → gen 0 (保护)        │  │  │

│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 核心流程

```
应用切换 (用户态)
    │
    ├──→ app_markov.py 预测: "下一个应用可能是 QQ"
    │    │
    │    └──→ 调整 demote_wmark (eBPF Map 传入内核)
    │            QQ cgroup: demote_wmark ↑ (留给它的空间更大，回收更温和)
    │            其他 cgroup: demote_wmark ↓ (积极回收，为 QQ 腾空间)
    │
    ▼
try_charge_memcg() 持续发生
    │
    └──→ done_restock:
          └──→ tier2_wmark_memcg_check_and_reclaim() [mm/tier2_watermark.c]
                │
                ├── headroom < alloc_wmark?
                │
                ├── headroom < demote_wmark?
                │     │
                │     └── YES → ──→ ★ 调用点: tier2_predict_adjust_pages() ★
                │                    │
                │                    │ ① 从 history_map 读取最近的 4 个操作
                │                    │ ② Markov 查表预测下一个操作
                │                    │ ③ 从 profile_map 查找该操作的页面范围
                │                    │ ④ 调整 MGLRU generation:
                │                    │    • 预测到的页面: 提升到 gen 0 (保护, 不被回收)
                │                    │    • 未预测到的页面: 降到 gen 3 (优先回收候选)
                │                    │
                │                    └──→ 进入 MGLRU 原有回收逻辑
                │                         ↓
                │                    lru_gen_shrink_lruvec()
                │                    从 gen 3 开始扫描 → 回收冷页
                │                    跳过 gen 0 (被保护的预测页面)
                │
                └── rate limit 16:1 → schedule_work(reclaim_work)
```

## 2. 预测模型详解（来自 huawei_mem）

### 2.1 应用间预测：`app_markov.py`

**文件**: `lzx/operation_predictor/src/models/app_markov.py`

**模型**: Horizon-specific Markov chain，支持 1-4 阶

```python
class AppMarkovModel:
    def __init__(self, order=4):
        # 按时间范围维护独立转移表
        self.transitions: dict[horizon][context_tuple] → Counter[next_app_id]
        self.global_counts: dict[horizon] → Counter[app_id]

    def fit(self, samples):
        for (context_apps, label_5min, label_10min, label_30min) in samples:
            for horizon, labels in [('5min', label_5min),
                                     ('10min', label_10min),
                                     ('30min', label_30min)]:
                # 构建 1-4 阶所有 context → label 转移
                for order in range(1, self.order + 1):
                    ctx = tuple(context_apps[-order:])
                    for next_app in labels:
                        self.transitions[horizon][ctx][next_app] += 1

    def predict_topk(self, context_apps, horizon, k=3):
        # 从高阶开始回退预测
        for order in range(self.order, 0, -1):
            ctx = tuple(context_apps[-order:])
            if ctx in self.transitions[horizon]:
                return self.transitions[horizon][ctx].most_common(k)
        # 回退到全局频率
        return self.global_counts[horizon].most_common(k)
```

**内核侧接口（eBPF Map）**:

```c
// demote_map: 应用 → demote 水位线调整系数
// Key: app_id (unsigned short)
// Value: demote_scale (unsigned int) — 万分比系数

struct bpf_map_def SEC("maps") demote_map = {
    .type = BPF_MAP_TYPE_HASH,
    .key_size = sizeof(unsigned short),
    .value_size = sizeof(unsigned int),
    .max_entries = 128,
};
```

**调整策略**：

| 预测结果 | demote_scale 调整 | 效果 |
|---------|------------------|------|
| 预测为下一应用 (如 QQ) | 降低 demote_scale (如 300→100) | 回收更温和，保护 QQ 的页面 |
| 未预测的应用 | 提高 demote_scale (如 300→500) | 回收更积极，释放空间 |
| 后台/无人使用 | 大幅提高 (如 300→800) | 激进回收，为前台应用腾空间 |

### 2.2 应用内操作预测：`op_markov.py`

**文件**: `lzx/operation_predictor/src/models/op_markov.py`

**模型**: 1-4 阶 Markov chain，预测应用内的下一步操作

```python
class OpMarkovModel:
    def __init__(self, order=4):
        # key: (app_id, context_tuple[1..order])
        self.transitions: dict[app_id][context_tuple] → Counter[next_op_id]

    def fit(self, samples):
        for (app_id, history_ops, label_next_op) in samples:
            # 为每个历史长度 (1..order) 建立转移
            for length in range(1, min(self.order, len(history_ops)) + 1):
                ctx = tuple(history_ops[-length:])
                self.transitions[app_id][ctx][label_next_op] += 1

    def predict_topk(self, app_id, history_ops, k=3):
        # 从高阶回退
        for order in range(self.order, 0, -1):
            ctx = tuple(history_ops[-order:])
            if app_id in self.transitions and ctx in self.transitions[app_id]:
                return self.transitions[app_id][ctx].most_common(k)
        # 回退到全局 op 频率
        return self.global_freq[app_id].most_common(k)
```

**内核侧接口（eBPF Maps）**:

```c
// 已有的 eBPF maps 结构 (来自 zb/MGLRU/ebpf/cache_ext_bpf_common.h)

// 操作历史环形缓冲
struct cache_ext_hist_key {
    unsigned short app_id;
};
struct cache_ext_hist_val {
    unsigned short ops[4];      // 最近 4 个操作
    unsigned char length;       // 有效操作数量
};

// Markov 转移表 (直接从 Python 模型导出)
struct cache_ext_markov_key {
    unsigned short app_id;
    unsigned short ctx[4];      // 4-order Markov 上下文
};
struct cache_ext_markov_val {
    unsigned short next_op;     // 预测的下一个操作
    unsigned int count;         // 转移频次 (置信度)
};

// 页面 Profile (操作 → 页面范围映射)
struct cache_ext_profile_key {
    unsigned short app_id;
    unsigned short op_id;
    unsigned int dev;           // 设备号
    unsigned long long ino;     // inode 号
};
struct cache_ext_profile_val {
    unsigned long long index_start;  // 文件页起始偏移
    unsigned long long index_end;    // 文件页结束偏移
    unsigned short priority;         // ★ 页面优先级 (0-100)
};
```

## 3. 内核侧实现方案

### 3.1 调用点

**位置**: `mm/tier2_watermark.c` — `tier2_wmark_memcg_check_and_reclaim()`

在 headroom 低于 demote_wmark 时，**先调用预测函数调整页面优先级，再进入回收逻辑**。

```c
bool tier2_wmark_memcg_check_and_reclaim(struct mem_cgroup *memcg)
{
    struct tier2_wmark_memcg *tm;
    unsigned long headroom, demote_wmark;
    // ... 现有水位线计算 ...

    // ========== 新增: 预测驱动的页面优先级预调整 ==========
    if (headroom < demote_wmark) {
        /*
         * 在触发回收之前，先调用 Markov 预测函数
         * 根据预测结果调整 MGLRU generation
         * 使回收时优先回收不需要的页面，保护预测即将使用的页面
         */
        tier2_predict_adjust_pages(memcg);
    }
    // ========== 新增结束 ==========

    // ... 原有回收逻辑 (rate limit + schedule_work) ...
}
```

### 3.2 核心函数：`tier2_predict_adjust_pages()`

**文件**: `mm/tier2_watermark.c`（新增）  
**风格**: 匹配现有 v3 内核代码风格（`struct tier2_wmark_memcg`、`atomic64_t`、MGLRU API）

```c
/*
 * tier2_predict_adjust_pages - 预测驱动的 MGLRU generation 调整
 * @memcg: 目标 memory cgroup
 *
 * 在触发回收前调用。读取 eBPF maps 中的 Markov 预测结果，
 * 根据预测到的下一个操作，调整对应页面的 MGLRU generation:
 *   - 预测页面: 视为即将使用 → 移到 gen 0 (youngest, 受保护)
 *   - 非预测页: 视为冷页 → 保持 gen 3 (oldest, 优先回收)
 *
 * 这样当后续 MGLRU 回收时，被保护的页面不会被回收。
 *
 * 调用路径:
 *   try_charge_memcg() → done_restock
 *     → tier2_wmark_memcg_check_and_reclaim()
 *       → tier2_predict_adjust_pages()        ← 本函数
 *       → schedule_work(reclaim_work)           ← 异步回收
 *         → tier2_wmark_reclaim_work_fn()
 *           → try_to_free_mem_cgroup_pages()
 *             → lru_gen_shrink_lruvec()         ← MGLRU 回收 (跳过 gen 0)
 *
 * 依赖的 eBPF Maps (由用户态预先填充):
 *   - history_map[app_id]        → 最近 4 个操作
 *   - markov_map[{app, ctx[4]}]  → 预测的 next_op + count
 *   - profile_map[{app, op, dev, ino}] → 页面范围 + priority
 */
void tier2_predict_adjust_pages(struct mem_cgroup *memcg)
{
    /*
     * ============================================================
     * 第 1 步: 获取当前应用的操作历史
     * ============================================================
     * 从 eBPF history_map 中读取最近 4 个操作。
     * history_map 由用户态代理在每次操作切换时更新。
     */
    struct cache_ext_hist_key hist_key = { .app_id = current_app_id() };
    struct cache_ext_hist_val *hist_val;

    hist_val = bpf_map_lookup_elem(&history_map, &hist_key);
    if (!hist_val || hist_val->length == 0)
        return;  /* 无操作历史，无法预测 */

    /*
     * ============================================================
     * 第 2 步: Markov 预测下一个操作
     * ============================================================
     * 构建 4 阶 Markov 查询 key，从高阶回退。
     * 这直接复现了 op_markov.py 中的 predict_topk() 逻辑。
     *
     * 回退策略 (从高阶到低阶):
     *   ctx = ops[len-4 .. len-1] → 查 markov_map
     *   ctx = ops[len-3 .. len-1] → 查 markov_map
     *   ctx = ops[len-2 .. len-1] → 查 markov_map
     *   ctx = ops[len-1]          → 查 markov_map
     *   若全未命中 → 使用全局频率 (profile_map 中 priority 最高的操作)
     */
    struct cache_ext_markov_key mkey;
    struct cache_ext_markov_val *mval = NULL;
    int ctx_len;

    mkey.app_id = hist_key.app_id;
    memset(mkey.ctx, 0, sizeof(mkey.ctx));

    for (ctx_len = hist_val->length; ctx_len >= 1; ctx_len--) {
        int start = hist_val->length - ctx_len;
        memcpy(mkey.ctx, &hist_val->ops[start],
               ctx_len * sizeof(unsigned short));
        mval = bpf_map_lookup_elem(&markov_map, &mkey);
        if (mval && mval->next_op != 0)
            break;  /* 命中 */
    }

    if (!mval || mval->next_op == 0) {
        /* 无预测: 不做调整, 让 MGLRU 正常回收 */
        return;
    }

    unsigned short predicted_op = mval->next_op;
    unsigned int confidence = mval->count;  /* 命中次数, 越大越可信 */

    /*
     * ============================================================
     * 第 3 步: 查找预测操作的页面范围
     * ============================================================
     * profile_map 记录了每个 (app, operation) → 文件页范围的映射。
     * 这些映射由用户态在应用首次运行时通过 page cache profiling 建立。
     *
     * 例如: QQ + "打开聊天窗口" → /data/app/qq/libwechat.so 的页 100-500
     */
    struct cache_ext_profile_key pkey = {
        .app_id = hist_key.app_id,
        .op_id  = predicted_op,
        /* dev 和 ino 需要遍历所有可能的文件 */
    };

    /*
     * ============================================================
     * 第 4 步: 调整 MGLRU generation — 核心逻辑
     * ============================================================
     *
     * MGLRU 将每个 lruvec 中的页面分为 4 代 (gen 0-3):
     *   gen 0: 最近访问 (最年轻, 回收优先级最低)
     *   gen 1: 较近访问
     *   gen 2: 较远访问
     *   gen 3: 最久未访问 (最老, 回收优先级最高)
     *
     * 调整策略:
     *
     * ┌────────────────────┬──────────────────────────────────┐
     * │ 页面分类           │ MGLRU Generation 调整              │
     * ├────────────────────┼──────────────────────────────────┤
     * │ 在 profile_map 中  │ 移到 gen 0 (youngest)             │
     * │ 匹配预测操作的页面 │ → 被视为"即将使用"                │
     * │                    │ → MGLRU 回收时跳过                │
     * ├────────────────────┼──────────────────────────────────┤
     * │ 同一 cgroup 内     │ 移到 gen 3 (oldest)               │
     * │ 非预测的页面       │ → 被视为"暂时不需要"              │
     * │                    │ → MGLRU 回收时优先处理            │
     * ├────────────────────┼──────────────────────────────────┤
     * │ confidence 较低    │ 仅部分移动 (如 50% 的页面)        │
     * │ (预测置信度不足)   │ → 保守策略, 避免误判              │
     * └────────────────────┴──────────────────────────────────┘
     *
     * 实现伪代码:
     *
     *   for_each_lruvec_in_memcg(lruvec, memcg) {
     *       for_each_page_in_profile(profile, page) {
     *           // 预测页面: 标记为 gen 0 (保护)
     *           lru_gen_set_gen(page, 0);
     *           SetPageWorkingset(page);  // 标记为工作集
     *       }
     *
     *       // 非预测页面: 如果当前在 gen 0-2, 移到 gen 3
     *       lru_gen_walk(lruvec, page) {
     *           if (!page_is_predicted(page))
     *               lru_gen_set_gen(page, MAX_NR_GENS - 1);
     *       }
     *   }
     *
     * 注意:
     * - lru_gen_set_gen() 是伪代码, 实际需要通过 MGLRU 的
     *   lru_gen_update_size() / set_mask_bits() 等内部 API
     * - SetPageWorkingset() 是已有的内核函数, 标记页面为工作集活跃
     * - 如果 MGLRU 未启用 (lru_gen_enabled() == false),
     *   则使用传统的 SetPageActive() / ClearPageActive() 替代
     */

    /*
     * 如果 MGLRU 启用:
     * 利用 lru_gen 的代际信息进行精细调整
     */
    if (lru_gen_enabled()) {
        tier2_predict_adjust_lru_gen(memcg, &pkey, predicted_op,
                                      confidence);
    } else {
        /*
         * 无 MGLRU 时的回退:
         * 使用传统的 active/inactive 标记
         */
        tier2_predict_adjust_active_list(memcg, &pkey, predicted_op);
    }
}
EXPORT_SYMBOL_GPL(tier2_predict_adjust_pages);
```

### 3.3 MGLRU Generation 调整实现

```c
/*
 * tier2_predict_adjust_lru_gen - 用 MGLRU 代际信息调整页面优先级
 *
 * 遍历 memcg 的每个 lruvec, 根据预测结果调整 generation:
 *
 *  预测页面: 标记 PG_workingset, 使其在 MGLRU 回收时被看作活跃页面
 *           移动对应 generation 的计数器, 使该页看起来像刚被访问
 *
 *  非预测页面: 降低 generation, 使其成为优先回收候选
 *
 * MGLRU 相关数据结构 (来自 include/linux/mmzone.h):
 *   struct lruvec {
 *       struct lru_gen_struct lrugen;  // MAX_NR_GENS = 4
 *   };
 */
static void tier2_predict_adjust_lru_gen(
    struct mem_cgroup *memcg,
    struct cache_ext_profile_key *pkey,
    unsigned short predicted_op,
    unsigned int confidence)
{
    int nid;
    struct lruvec *lruvec;

    /*
     * 对每个 NUMA node 上的该 cgroup LRU 进行处理
     */
    for_each_online_node(nid) {
        lruvec = mem_cgroup_lruvec(memcg, NODE_DATA(nid));

        /*
         * 遍历 profile_map 中所有匹配 (app, op) 的条目,
         * 将其对应的页面标记为高优先级
         *
         * 匹配条件:
         *   pkey.app_id == profile_key.app_id &&
         *   pkey.op_id  == profile_key.op_id
         *
         * 对于匹配的文件页面:
         *   通过 find_get_page(ino, index) 或 address_space 定位页面,
         *   然后:
         *     1. SetPageWorkingset(page)   — 标记为工作集页面
         *     2. lru_gen_inc_gen(page)      — 提升 generation (如果有 API)
         *     3. 或直接调用 folio_activate() — 提升到活跃 LRU
         *
         * 实际上, MGLRU 没有直接的 "set generation" API。
         * 替代方案:
         *   a) mark_page_accessed(page)    — 标记页面为最近访问,
         *      这会触发 MGLRU 将该页移到 gen 0
         *   b) folio_mark_accessed(folio)  — 等价效果
         *
         * 对预测页面调用 mark_page_accessed():
         *   使 MGLRU 在下次 aging 时将页面移到 gen 0 (受保护)
         *
         * 对非预测页面调用 folio_deactivate():
         *   使 MGLRU 将页面移到 inactive/gen 3 (优先回收)
         */
    }

    /*
     * 性能考量:
     * - 只在 headroom < demote_wmark 时调用, 已有 rate limit
     * - 每次最多处理 nr_pages = SWAP_CLUSTER_MAX (32) 个页面
     * - 遍历 profile_map 时加 rcu_read_lock
     * - 使用 folio_try_get() 避免竞争
     */
}
```

### 3.4 与 MGLRU 回收的衔接

调整完 generation 后，正常的 MGLRU 回收路径自动受益：

```c
/*
 * 流程: tier2_predict_adjust_pages() 调整后
 *        → schedule_work(&reclaim_work)
 *          → tier2_wmark_reclaim_work_fn()
 *            → try_to_free_mem_cgroup_pages(memcg, nr, ...)
 *              → shrink_lruvec(lruvec)
 *                → lru_gen_shrink_lruvec(lruvec)  [MGLRU 路径]
 *
 * MGLRU shrink 的核心逻辑 (mm/vmscan.c):
 *
 *   lru_gen_shrink_lruvec(lruvec):
 *     for gen = MAX_NR_GENS-1; gen >= 0; gen--:  // 从 gen 3 到 gen 0
 *       for each page in lrugen->lists[gen][type]:
 *         if PageWorkingset(page):
 *           continue;  // ★ 跳过工作集页面 (我们标记的预测页面)
 *         if try_to_reclaim(page):
 *           nr_reclaimed++;
 *
 * 因为我们已经把预测页面标记为 PG_workingset,
 * 这些页面会在 shrink 时被 MGLRU 跳过,
 * 而非预测页面 (保持在 gen 3, 无 PG_workingset) 会被优先回收。
 */
```

## 6. eBPF 未启用时的回退

当 eBPF maps 不可用时（如非 huawei_mem 环境），`bpf_map_lookup_elem()` 返回 NULL，函数直接 return，完全 no-op。内核行为与现有 v3 完全相同。

```c
void tier2_predict_adjust_pages(struct mem_cgroup *memcg)
{
    hist_val = bpf_map_lookup_elem(&history_map, &hist_key);
    if (!hist_val || hist_val->length == 0)
        return;  // ★ 回退: 无操作历史, 不做任何预测调整

    mval = bpf_map_lookup_elem(&markov_map, &mkey);
    if (!mval || mval->next_op == 0)
        return;  // ★ 回退: Markov 未命中, MGLRU 正常回收

    // ... 有预测时才调整 generation ...
}
```

## 9. 总结

本方案基于 huawei_mem 仓库中的 **Markov 预测模型** + **eBPF maps 基础设施** + **MGLRU generation 机制**，在 v3 内核的 `mm/tier2_watermark.c` 中实现预测驱动的页面优先级预调整。

**核心思路**：
1. 用户态 Markov 模型预测"下一个应用"和"下一步操作"
2. 预测结果通过 eBPF maps 传入内核
3. 当内存压力到达 demote 水位线时，调用 `tier2_predict_adjust_pages()`
4. 预测到的页面 → MGLRU gen 0 (保护)
5. 非预测页面 → MGLRU gen 3 (优先回收)
6. MGLRU 回收时自动跳过被保护的页面

**关键特性**：
- 纯增量修改，调用点仅在 `mm/tier2_watermark.c`
- eBPF maps 为空时完全 no-op
- 与现有 rate limit 机制自然集成
- 不改动 MGLRU shrink 核心逻辑
